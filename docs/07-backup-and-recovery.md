# Как поднять агента из бэкапа — по шагам

Инструкция для человека, а не для программиста. Делай строго сверху вниз, ничего
не пропускай. Где надо что-то вставить — вставляешь целиком блок и жмёшь **Enter**.

**Держи под рукой (это должно лежать НЕ на сервере — в заметках/менеджере паролей):**
- Пароль от бэкапа. Бот агента прислал его тебе файлом `backup-password-<агент>.txt`
  при установке. Не нашёл — попроси агента «пришли пароль от бэкапа» (он запустит
  `scripts/backup-pass-send.sh --force`), пока сервер жив.
- Доступ к Google Drive, где лежит бэкап (папка `dashi-<имя-агента>-backups`).
- Доступ к GitHub (аккаунт `popovalex17071985-source`).
- Root-пароль от сервера (в панели хостинга).

Дальше `<агент>` = имя твоего агента (например `lena`). Подставляй везде своё.

---

# Случай 1. Бот молчит, но сервер жив (забанили Claude)

Самый лёгкий. Сервер и данные целы — просто заново войти в Claude.

**Шаг 1.** Зайди на сервер. На Mac открой программу «Терминал», впиши (свой IP
вместо `АЙПИ`) и нажми Enter, потом введи root-пароль:
```
ssh root@АЙПИ
```
> На Mac перед этим **выключи VPN** — иначе не пустит.

**Шаг 2.** Получи новый годовой токен. Впиши:
```
su - agent -c 'claude setup-token'
```
Появится длинная ссылка — открой её в браузере на телефоне/компе, войди в
**тот же** аккаунт Claude, что был раньше, скопируй код со страницы, вернись в
терминал, вставь код, Enter. В конце на экране напечатается токен — длинная
строка, начинается с `sk-ant-oat01-`. Скопируй её целиком.

**Шаг 3.** Отдай токен установщику (замени `ТОКЕН` на скопированную строку):
```
sudo bash dashi-plugin-claude-code/scripts/install-agent.sh --name <агент> --claude-token ТОКЕН
```
Он запишет токен куда надо и сам перезапустит агента.

**Шаг 4.** Напиши боту в Telegram. Ответил — всё, готово.

# Случай 2. Сервер умер (нужен новый с нуля)

**Шаг 0. Старый сервер — ВЫКЛЮЧИ.** Если старый сервер ещё хоть как-то жив
(завис, тормозит, «вроде умер»), сначала выключи его в панели хостинга
(«Выключить» / «Stop»). Не перезагрузить — именно выключить. Иначе после
восстановления на одном боте окажутся два агента: сообщения будут доставаться
то одному, то другому, а расписание и рассылки пойдут дважды. Команда
восстановления спросит «Старый сервер выключен?» и без «y» дальше не пойдёт.

**Шаг 1. Купи новый сервер.** У любого хостинга закажи VPS с **Ubuntu 22.04**.
После оплаты тебе дадут **IP-адрес** и **root-пароль** (на почту или в панели).

**Шаг 2. Зайди на сервер.** На Mac открой «Терминал», впиши (свой IP вместо
`АЙПИ`), Enter, введи root-пароль:
```
ssh root@АЙПИ
```
> VPN на Mac выключи.

**Шаг 3. Скачай код агента.** Скопируй строку целиком, вставь, Enter:
```
K=КЛЮЧ_ДОСТУПА   # репозиторий закрытый: ключ только на чтение выдаёт хозяин репозитория
git clone https://x-access-token:$K@github.com/popovalex17071985-source/JohnRamboAgent.git dashi-plugin-claude-code
```
> Папка должна называться `dashi-plugin-claude-code` — дальше команды обращаются
> к ней по этому имени.

**Шаг 4. Возьми бэкап.** Открой Google Drive в браузере, зайди в папку
`dashi-<агент>-backups`, скачай **самый свежий** файл (имя вида
`<агент>-20260824-0340.tar.gz.gpg`). Затем закинь его на сервер — проще всего
так, с СВОЕГО компа (не с сервера), в новом окне терминала:
```
scp ~/Downloads/<агент>-20260824-0340.tar.gz.gpg root@АЙПИ:/root/
```
> Тут `~/Downloads/...` — куда браузер скачал файл; `АЙПИ` — адрес сервера.
> Если запутался на этом шаге — зови меня или айтишника, остальное дальше простое.

**Шаг 5. Одна команда восстановления.** Вернись в окно, где ты на сервере
(`root@...`). Вставь целиком, Enter:
```
sudo bash dashi-plugin-claude-code/scripts/restore-agent.sh \
     --name <агент> \
     --archive /root/<агент>-20260824-0340.tar.gz.gpg
```
Сначала она спросит **«Старый сервер выключен?»** — ответь `y` (только если
правда выключен, см. шаг 0). Потом **спросит пароль от бэкапа** — впиши тот самый
пароль из файла, который прислал бот, Enter. (Пароль не отображается при вводе —
это нормально.)

Дальше она всё делает сама:
- раскладывает домашнюю папку агента целиком — память, характер, секреты и всю
  его работу: скрипты, данные, папки проектов рядом с ним;
- ставит программы, которые стояли на старом сервере (список пакетов едет в архиве);
- заново собирает окружения Python (venv) той же версией Python, что была;
- возвращает расписание (крон), создаёт папки для логов, запускает его сервисы;
- ставит серверу тот же часовой пояс, что был на старом (иначе всё расписание
  съедет на несколько часов).

**Шаг 6. Дождись «агент <агент> восстановлен».** Это займёт от нескольких минут
до получаса (ставит программы). Если в конце есть список **«Не доделано»** — агент
всё равно работает, а в списке написано, что доделать руками и какой командой.
Самое частое:
- «нет pythonX.Y» — на новом сервере другой Python. Команда для установки
  написана прямо в строке; после неё:
  `sudo bash dashi-plugin-claude-code/scripts/restore-agent.sh --name <агент> --envs-only`
- «доп. пути лежат в …/extra» — у агента были папки вне его домашней папки
  (например `/opt/…`). Они в архиве, но на место сами не встают: перенеси их
  командой, которую она напечатала (или позови меня/айтишника). Если среди них
  `/opt/repair-<агент>` (бот-ремонтник) — после переноса запусти установщик ещё
  раз: `sudo bash dashi-plugin-claude-code/scripts/install-agent.sh --name <агент>`.
  Python и окружение ремонтника в архив не идут, установщик ставит их заново.

**Проверь облако.** Облачная копия на новом сервере должна снова начать
уезжать. Вход в Google Drive едет в архиве, но Google иногда просит войти заново.
Проверка (в окне сервера):
```
sudo -iu agent rclone lsd gdrive:
```
Показал папки — всё хорошо. Ошибка про «token»/«invalid_grant» — войди заново
(раздел «Google Drive» ниже) или напиши агенту «подключи облако для бэкапа». Если
забудешь — на следующий день агент сам напишет, что бэкап не уезжает в облако.

Команду восстановления можно запускать повторно: второй раз она не распаковывает
архив заново и ничего не затирает, а только доделывает недостающее.

**Шаг 7. Напиши боту в Telegram.** Вход в Claude обычно НЕ нужен — годовой
токен приезжает из бэкапа вместе с настройками. Ответил — агент воскрес.

Молчит дольше пары минут — значит токен успел протухнуть (ему год): сделай
Случай 1, шаги 2–3, и напиши боту снова.

## Если что-то пошло не так

- «пароль неверный» на шаге 5 → перепроверь пароль от бэкапа (без лишних пробелов).
- Файл на сервер не закидывается (шаг 4) → это единственное реально муторное
  место, зови айтишника или меня с другого сервера — покажу.
- Всё остальное делает одна команда; если она дошла до «восстановлен» — данные целы.

## Полезное про сам бэкап (можно не читать)

Бэкап делается сам раз в сутки (`scripts/agent-backup.sh`, крон в 03:40): один
зашифрованный файл со **всей домашней папкой агента** — память, характер,
секреты, токен бота, расписание и вся его работа (скрипты в `~/bin` и
`~/.local/bin`, данные, папки проектов рядом с ним). Хранится 7 последних копий;
если подключено облако — копия уезжает туда (**только облачная копия переживёт
смерть сервера**). Каждая свежая копия сразу проверяется на расшифровку — битую
бэкап удаляет сам.

**Что НЕ кладётся в архив** — список в `deploy/backup-exclude.txt` в папке агента:
кэши, `node_modules`, содержимое логов (сами папки логов остаются), сами архивы,
копия плагина с GitHub. Его можно править: одна строка — один путь
(`~/путь`, `/абс/путь` или просто имя). Окружения Python (venv) в архив не идут
целиком — едет список пакетов и версия Python, на новом сервере они собираются
заново. Так же с пакетами, поставленными `pip install --user` (папка
`~/.local/lib/python3.*`, бывает больше гигабайта): едет их список, восстановление
ставит их заново. Ещё в архиве: список программ сервера (`apt`), свои сервисы агента,
расписание.

Твой список исключений плагин не переписывает. Когда в обновлении появляется новое
исключение по умолчанию, бэкап один раз дописывает его в конец списка с пометкой
«добавлено обновлением плагина». Не нужно — закомментируй строку (`#` в начале),
а не удаляй: удалённая вернётся. Дописать прямо сейчас, не дожидаясь ночи:
```
sudo -u agent DASHI_AGENT=<агент> DASHI_WORKSPACE=/home/agent/.claude-lab/<агент> \
  bash /home/agent/.claude-lab/<агент>/.claude/dashi-plugin-claude-code/scripts/agent-backup.sh --init-excludes
```

**Папки вне домашней папки агента** (например `/opt/моё-приложение`, свои сайты
nginx) сами в архив не попадают — впиши их по одной в `deploy/backup-extra-paths`.

**Сколько весит и что попадёт** — без создания архива:
```
sudo -u agent DASHI_AGENT=<агент> DASHI_WORKSPACE=/home/agent/.claude-lab/<агент> \
  bash /home/agent/.claude-lab/<агент>/.claude/dashi-plugin-claude-code/scripts/agent-backup.sh --size-report
```

**Сторож облачной копии.** Каждый день в 11:20 агент проверяет, есть ли в облаке
копия моложе 48 часов. Бот присылает тебе сообщение, что не так и где смотреть,
если:
- облако не подключено;
- облако не отвечает (чаще всего истёк вход в Google) — тогда неизвестно, есть ли
  там свежая копия;
- на диске не хватает места на новый архив (бэкап тогда ничего не пишет, прошлые
  копии целы);
- копии в облаке старше 48 часов (Google отозвал вход, кончилось место);
- последняя ночная отправка в облако не удалась — даже если вчерашняя копия ещё
  там (так беда видна в первый же день, а не через двое суток);
- «облако» на самом деле папка на этом же сервере — такая копия умрёт вместе с ним.

Когда всё хорошо — молчит. Для тестового сервера, где облако нарочно заменено
папкой, это объявляется явно файлом `deploy/offsite-stub` (одна строка — зачем);
тогда сторож пишет в свой лог «STUB», не «OK», и никого не тревожит. На боевом
агенте такого файла быть не должно. Если хочешь, чтобы такое сообщение приходило ещё
кому-то (этот человек должен сначала нажать Start у бота), впиши его id в
`/etc/dashi-plugin/<агент>/channel.env` строкой `DASHI_BACKUP_ALERT_CHATS=id1,id2`.

**Пароль ещё раз.** Пока сервер жив, пароль можно прислать себе заново:
```
sudo -u agent DASHI_AGENT=<агент> DASHI_WORKSPACE=/home/agent/.claude-lab/<агент> \
  bash /home/agent/.claude-lab/<агент>/.claude/dashi-plugin-claude-code/scripts/backup-pass-send.sh --force
```

Проверить, что восстановление вообще рабочее, не дожидаясь ЧП (ничего живого не
трогает, нужен docker):
```
bash tests/restore-agent-home-e2e.sh   # бэкап всей домашки -> чистый сервер
bash tests/restore-agent-e2e.sh        # старый формат архива + полный установщик
```

_Главное: держи ВНЕ сервера пароль от бэкапа и доступ к GitHub/Google Drive. Без
них не восстановит никто, с ними — восстановит любой._

## Google Drive: свой ключ обязателен (иначе «квота превышена»)

**Симптом:** `rclone` начинает падать с ошибкой квоты — листинг папки то проходит,
то нет, скачивание файла не проходит вовсе. Диск при этом свободен.

**Причина:** по умолчанию rclone ходит в Google под СВОИМ общим ключом, одним на
всех пользователей rclone в мире. В часы пик этот общий лимит выбирается чужими
людьми, и твой бэкап просто не доезжает. Паузы между запросами (`pacer-min-sleep`)
лечат симптом частично и не лечат причину.

**Лечится один раз, за 5 минут, бесплатно** — заводится собственный ключ. Биллинг
и карта не нужны.

1. Открой https://console.cloud.google.com/ под тем же Google-аккаунтом, где лежит
   Drive агента. Создай проект (любое имя, например `dashi-backups`).
2. «APIs & Services» → «Library» → найди **Google Drive API** → **Enable**.
3. «APIs & Services» → «OAuth consent screen» → тип **External** → заполни только
   обязательные поля → в разделе «Test users» добавь свой же Google-адрес.
4. «APIs & Services» → «Credentials» → «Create credentials» → **OAuth client ID** →
   тип **Desktop app**. Скопируй выданные `Client ID` и `Client secret`.
5. На сервере агента: `rclone config` → `e` (edit remote) → выбери `gdrive` →
   вставь свой `client_id` и `client_secret` → дальше по умолчанию, авторизацию
   подтверди в браузере.
6. Проверь: `rclone about gdrive:` — должен отдать размеры, а не ошибку.

Проверить, есть ли свой ключ уже сейчас:

```bash
grep -c client_id ~/.config/rclone/rclone.conf   # 0 = сидишь на общем, надо заводить
```

Пока своего ключа нет — бэкап работает «как повезёт»: в тихие часы проходит, в пик
падает. Это не поломка агента и не поломка сервера.
